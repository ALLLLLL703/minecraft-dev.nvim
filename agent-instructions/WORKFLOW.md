# 开发工作流

## 调查与设计

1. 确认用户要求的公开行为、范围、非目标和完成条件。
2. 读取相关公共入口、实现、测试、设计文档和调用方；对 Neovim API 核对官方文档。
3. 对标上游时检查 `minecraft-dev/MinecraftDev` 及 templates 仓库，记录参考提交，并区分可直接映射、需要 Neovim 适配和不适用的能力。
4. 新增通用能力或依赖前，先检查 Neovim 内置 API、现有依赖和维护良好的外部实现；选择应说明兼容性、维护成本和回退行为。

## 实现

1. 按可独立验证的纵向行为切片推进：公共行为、最小实现、测试和文档一起完成。
2. 优先扩展现有注册表、规范化流程和生成接口，不建立重复的平台列表或平行旧实现。
3. 新配置必须具有默认值、规范化/校验规则、文档和测试；新命令必须覆盖参数、补全、取消、错误及重复加载。
4. 外部命令、网络和文件任务保持异步，明确成功、错误、取消、清理和回调生命周期。
5. 行为变化同步更新适用的 README、help、公共 API 文档或 `DESIGN.md`。

## 验证

- 测试入口和 Neovim 实例要求遵循 `agent-instructions/MCP.md`。
- 测试优先经过真实公共入口，覆盖成功路径以及最重要的错误、取消或边界路径。
- Bugfix 必须有能在旧实现上失败的回归场景；不得削弱测试来换取通过。
- 生成器变更至少在临时目录验证真实项目结构；构建文件、依赖或版本变更应进一步执行 Gradle/Maven 解析或构建。
- 命令、配置、插件加载或启动路径变化后，必须验证 Neovim 仍可正常交互启动，不得留下错误循环、 hit-enter 阻塞或无法进入编辑界面的路径。
- 网络相关测试使用稳定 fixture 或明确的离线回退，不能让基础测试依赖不稳定在线服务。
- 未执行或环境受限的验证必须说明原因及残余风险，不能写成已经通过。

## Git

- Git 只包含当前阶段的相关文件，不暂存或提交用户及其他代理的无关变更。
- 每完成一个可独立验证的实现阶段后提交一次；提交信息使用英文并描述可观察行为。
- 每次提交完成后使用 GitHub MCP 推送，并确认远端包含目标提交。
- 禁止通过强推、重置、清理或跳过钩子解决失败。遇到远端分叉或不明状态时停止并通过 `question` 工具确认。
- 阶段完成前检查工作树、目标 diff 和验证结果，移除临时调试代码、生成物及实验性绕过。
