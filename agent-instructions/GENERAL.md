# 通用仓库规则

## 指令优先级

- 修改某个子系统前，查找并读取覆盖该路径的 `AGENTS.md`、`STYLE.md` 和 `DESIGN.md`。
- `agent-instructions/STYLE.md` 是仓库编码风格的唯一事实来源，不在其他规则文件中重复风格条款。
- 先调查现有代码、测试、公共接口和调用关系，再形成结论或开始修改；不要凭文件名或记忆猜测行为。

## 沟通与决策

- 面向用户的内容输出，以及写入文件的内容总结，使用中文。
- 代码标识符、代码注释和 Git 提交信息使用英文，并遵循文件已有语言。
- 所有需要用户回答的问题都通过 `question` 工具提出。
- 遇到需求歧义、重要设计分支、兼容策略或停止条件不明确时必须提问，不得静默猜测。
- 完成变更后说明行为变化、设计原因、验证结果、兼容影响、已知限制和剩余风险，不能只给文件列表。

## 工具与资料

- MCP 选择、首次尝试、回退和证据记录统一遵循 `agent-instructions/MCP.md`。
- Neovim API 还应优先核对官方帮助和官方文档。
- 实现 MinecraftDev 对标能力时，经常检查 `minecraft-dev/MinecraftDev` 的对应实现，但只移植适合 Neovim 的行为。

## 实现原则

- 编写、重构或审查应用代码时使用 `maintainable-code`；需要压力测试方案或细化决策树时使用 `grill-me`。
- 优先做最小且完整的行为切片，不引入占位模块、无当前调用者的抽象、静默降级或测试输入特判。
- 修复共享失败机制，而不是只修复报告中的单个版本、平台或项目名。
- 不覆盖、撤销、格式化或提交用户及其他代理的无关变更。
- 用户可见行为、公共 API、配置或依赖发生变化时，同步更新 README、help 或对应设计文档。

## 长任务

- 执行跨多个调查、实现或验证阶段的长任务时，必须在仓库根目录维护 `todo.md`。
- `todo.md` 必须按阶段使用 Markdown 标题组织，并以 checklist 记录待办、进行中和已完成工作。
- 每完成一个阶段或任务范围发生变化时立即更新 checklist，确保文件反映真实进度、验证结果和剩余工作。
