# 代码审查规则

## 范围与证据

- 先确认审查基准，并覆盖相关 staged、unstaged 和 untracked 文件，不得静默忽略混合工作树的一部分。
- 先概括变更声称提供的行为、影响模块和完成条件，再检查实现、调用方、测试、文档和适用设计约束。
- 公共 API、配置、命令、模板协议、生成文件或依赖变化必须追踪到所有重要生产者和消费者。

## 审查重点

- 优先发现正确性缺陷、行为回归、路径逃逸、半成品输出、主线程阻塞、重复回调、取消/超时清理错误和缺失测试。
- 检查成功、错误、取消、重试、部分初始化和清理路径，确认错误保留有用上下文且不会静默降级。
- 检查平台、构建系统、语言和版本能力是否由单一注册来源驱动，避免调用方之间产生能力漂移。
- 检查 Neovim API 用法、重复加载、可选依赖回退、配置归一化和用户消息路径是否符合 `STYLE.md`。
- 生成器审查必须核对依赖坐标、仓库、Java/插件版本、元数据格式、入口源码和构建结果，而不只检查文件存在。
- 上游同步审查必须核对参考提交、许可证边界、Neovim 语义适配和明确不支持项，不能把 IntelliJ 专属行为伪装成已实现。
- 测试必须通过公共行为捕获所声称的问题。测试名特判、弱断言、忽略错误和不稳定在线依赖属于缺陷。

## 输出

- Findings 优先，按严重程度排序，并提供文件和行号、触发条件、影响及可执行修复方向。
- 区分本次引入的问题、被本次放大的既有问题和可选改进；没有行为或维护影响的个人偏好不是 finding。
- 如果没有发现问题，明确说明，并列出未验证场景或残余风险。
- 简短总结放在 findings 之后。审查默认只读，除非用户明确要求同时修复。
